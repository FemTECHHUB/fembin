Frontend integration guide

Everything a frontend needs to build against the fembin API: how auth works, what each endpoint expects and returns, and — more importantly — the rules that aren't visible in a schema, like why a quotation needs a sales person from a specific list, or why "success" doesn't mean "posted to BUSY."

Base URL  http://<host>/api/v1 Auth  Bearer JWT Format  JSON

Overview

fembin sits between BUSY — the desktop accounting software a physical repair business runs on — and everything else: a website, an internal sales app, and (later) a loyalty scheme. It mirrors BUSY's data into its own MySQL database for fast reads, and queues every write back to BUSY so a slow or flaky BUSY connection never blocks a request.

The one workflow fully built today is Sale Quotations — a rep picks products, a sales person, and a customer, and the quotation is queued to be posted into BUSY. Everything else (products, branches, sales people) is read-only reference data mirrored from BUSY for the frontend to build pickers from.

Two actors Most endpoints are for a logged-in rep — scoped to their own branch automatically. A handful are superadmin-only — cross-branch visibility and anything that writes to a live external system (creating users, setting a barcode, pushing to the website). The docs below mark each endpoint.

Conventions

Requests

Every endpoint is under /api/v1. Authenticated ones expect:

Authorization: Bearer <token>
Content-Type: application/json

Errors

Validation errors (missing/malformed fields) return FastAPI's standard shape with 422: 

{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "sales_person_id"],
      "msg": "Field required"
    }
  ]
}

Business-rule errors (wrong credentials, a code that doesn't match anything, a duplicate) return a flat shape instead: 

{ "detail": "sales_person_id does not match a known, active sales person" }

Always read detail — it's either an array (422) or a string (everything else). See Errors for the full status-code table.

Money and dates

  • Prices/amounts are decimal strings on the wire (e.g. "1000.00"), not JSON numbers — send and parse them as strings to avoid float rounding.
  • Quotation dates are DD-MM-YYYY — this is BUSY's own format, not ISO 8601.

Authentication

Username/password login returns a JWT. Every other endpoint (except the public catalog reads) expects it as a Bearer token. There's no refresh endpoint yet — tokens last 8 hours (one shift); re-login when one expires.

There's no self-service signup POST /auth/users requires an existing superadmin's token. The very first superadmin can't be created over HTTP at all — it's bootstrapped once from a server-side script (scripts/create_superadmin.py). If you need a test account, ask for one to be created rather than expecting a signup form to work.

Login → store token → attach to every request

// 1. Log in
const res = await fetch("/api/v1/auth/login", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ username, password }),
});
const { access_token } = await res.json();

// 2. Attach it to every subsequent request
await fetch("/api/v1/quotations", {
  headers: { "Authorization": `Bearer ${access_token}` },
});

Once you have a token, GET /auth/me tells you who you're acting as — critically, which branch (material_center_code) every action from this session will be scoped to. Fetch it right after login and use it to label the UI ("You're working from: Main Store").

Core concepts

The schemas are simple; the reasons behind them aren't obvious from the wire shape alone. Read this before wiring up the quotation form — it explains why several fields are required, or missing, on purpose.

Material Center = branch

Every user belongs to exactly one branch. You never send a branch on a quotation — it's always taken from the logged-in user, server-side. A rep at "Main Store" cannot post to, or see, another branch's quotations, and the API doesn't expose a way to override that from the client.

Sales person ≠ logged-in user

Several people can share one till/login. sales_person_id is a required, separate field — who actually made the sale. It's pulled live from BUSY (its "Engineer" list, in this business), not something the app lets you create. Always populate the picker from GET /sales-people.

Posting is asynchronous

POST /quotations returns 202 the instant it's queued — before BUSY has seen it. status: "queued" does not mean posted. Poll GET /outbox/:id (or re-fetch the list) until it flips to done or failed. See the full flow.

Barcode is local, not from BUSY

BUSY has no barcode field for this company. Product.barcode is assigned inside this app by a superadmin and never overwritten by a catalog sync. If it's null, that product just hasn't been assigned one — not a sync failure.

Building a quotation, end to end

This is the one workflow with real business logic behind it. Everything else in this API exists to feed this form. Walk through it once and the rest of the reference below will make sense in context.

  1. Log in, read /auth/me

    Get the token and the caller's material_center_name — show it in the UI so the rep knows which branch they're posting for.

  2. Load pickers in parallel

    GET /products?active=true and GET /sales-people. Both are unauthenticated-safe reads, but send the token anyway for consistency.

  3. Let the rep build the item list

    Pick a product (or match a scanned barcode against the already-loaded product list's barcode field — this is a client-side lookup, there's no barcode-search endpoint). Compute amount = qty × price yourself; BUSY expects a pre-calculated amount, it will not compute it for you.

  4. Require a sales person

    Don't let the form submit without one selected — the API will reject it with 422, but catching it client-side gives a much better error than a round trip.

  5. Generate an idempotency key once, client-side

    A UUID is fine. If the request times out and you retry with the same key, you get back the original job instead of creating a duplicate quotation. Generate a new key only when the rep starts a genuinely new quotation.

  6. POST /quotations → 202

    The response is an outbox job with status: "queued". This is not confirmation it reached BUSY — just that it's safely recorded and will be attempted.

  7. Poll until it resolves

    Re-fetch GET /outbox/{id} every few seconds (the reference console polls every 4s). Stop when status is done (show result.vch_no — the real BUSY voucher number) or failed (show last_error).

A queued job can sit there indefinitely The background worker that actually talks to BUSY is opt-in per environment. If nothing is moving past queued, that's an operational/config question, not a bug in your polling — surface a "still processing" state rather than assuming failure after a fixed timeout.

Active sales people, straight from BUSY. This is the picker source for the quotation form's sales_person_id field.

This list can legitimately be empty It reflects whatever is entered in BUSY at that moment. An empty array means "no one's been added in BUSY yet" — not a broken request. Render a clear empty state ("no sales people yet — add one in BUSY") rather than a spinner or a silent disabled form.

GET /quotations Auth required

Every quotation from the caller's own branch, newest first — same shape as the create response. This is what a status/history screen polls.

200 OK — once a job settles
{
  "status": "done",
  "result": { "vch_code": "9928", "vch_no": "RCC-5" }
}

result.vch_no is the real number BUSY assigned — that's what should go on a printed slip, never anything computed client-side.

GET /outbox/{id} Auth required

Look up one job by id — same shape, useful when you only kept the id from the create response rather than re-listing everything.

Unknown id → 404.

Sync & WooCommerce

Mostly superadmin/ops tooling — a normal rep-facing UI won't call these.

POST /sync/products Auth required

Kick off a fresh pull from BUSY (material centers, products, sales people) and a WooCommerce push. Runs in the background — the response doesn't wait for it.

Request body
{ "full": false } // true = ignore checkpoints, re-pull everything
202 Accepted
{ "status": "scheduled" }
GET /sync/status No auth

When each entity last synced, and the last WooCommerce push's tally — good for an ops/health screen.

POST /sync/woocommerce/push Superadmin

Push specifically chosen products to the live website right now, instead of waiting on the periodic sync.

Request body
{ "busy_codes": [1613, 1614] }
200 OK
{ "results": [
  { "busy_code": 1613, "name": "Cable-infinix Micro", "action": "created" },
  { "busy_code": 1614, "name": "Cable-infinix Typ C", "action": "skipped" }
] }

action is one of created, updated, skipped (already in sync), failed, not_found. WooCommerce not configured yet → 409.

Admin — cross-branch views

Identical shapes to their rep-facing equivalents, just without the branch filter. All superadmin-only.

GET /admin/users Superadmin

Every user, every branch.

GET /admin/quotations Superadmin

Every quotation, every branch — same shape as GET /quotations.

GET /admin/sales-people Superadmin

Every synced sales person, including inactive ones — useful for "who got blocked in BUSY" visibility that the public picker deliberately hides.

Working examples

Two plain HTML/JS pages already implement everything above, end to end, against this same API — reading the source is often faster than re-deriving the flow from this document.

/console

The rep-facing flow: login, product + barcode picker, sales-person picker, quotation submit, live status polling.

/admin

The superadmin flow: cross-branch views, barcode assignment, the WooCommerce push checklist.

Both are served by the backend itself (app/static/console.html, app/static/admin.html) — no build step, no framework, just fetch() against the exact endpoints documented above.

Token lifetime

8 hours from issue. There's no refresh flow — a session that's been idle across a shift boundary should just prompt for login again rather than trying to silently recover.
